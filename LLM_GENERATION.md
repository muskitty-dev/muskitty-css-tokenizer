# LLM Authorship Disclosure

This document discloses the LLM authorship of `muskitty-css-tokenizer`,
in accordance with This Week in Rust's submission policy.

## Summary

The CSS tokenizer logic in this crate was generated by an LLM-based
coding agent (GLM-5.2 via TRAE IDE), supervised by a human developer.
The crate was extracted from `muskitty-css` (commit 49ce0fb in the
workspace root) as a standalone crate to allow reuse by syntax
highlighters, CSS linters, and other parsers without dragging in the
full CSS parser or selector modules.

## Origin

This crate was originally developed inside `muskitty-css` as the
`src/tokenizer/` module. See
[muskitty-css/LLM_GENERATION.md](https://github.com/Ink-dark/MusKitty/blob/main/crates/muskitty-css/LLM_GENERATION.md)
for the full LLM authorship disclosure covering the tokenizer's
implementation history, test-feedback loop, and spec citation discipline.

## What the LLM Did

1. **Implemented the tokenizer** (CSS Syntax §4.3) — all 15 sub-algorithms
   of the CSS tokenizer, including:
   - Recursive-descent dispatch via `consume_a_token` (§4.3.1)
   - Comment consumption with EOF handling (§4.3.2)
   - Numeric token consumption with dimension/percentage disambiguation
     (§4.3.3)
   - Ident-like token consumption with `url(` special-casing (§4.3.4)
   - String token consumption with bad-string detection (§4.3.5)
   - URL token consumption with bad-url recovery (§4.3.6)
   - Escape sequence processing (§4.3.7) including null/surrogate
     replacement
   - Lookahead predicates for ident/number/unicode-range dispatch
     (§4.3.8–§4.3.11)
   - Ident sequence consumption with hex-escape decoding (§4.3.12)
   - Number parsing with integer/float flag (§4.3.13)
   - Unicode-range token consumption with `?` wildcard expansion
     (§4.3.14)
   - Bad-url remnants consumption (§4.3.15)
   - §5.3 input preprocessing (CR/LF/FF normalization)
   - §4.3.1 `unicode_ranges_allowed` flag for `@font-face` descriptor

2. **Diagnosed and fixed its own bugs** — when the test harness
   reports a failure, the agent reads the failing input, the expected
   output, and the relevant spec section, then proposes a fix.

3. **Selected Rust idioms** — the agent chose `Vec<char>` for the
   input stream, `peek`/`consume`/`reconsume` primitives, and
   exhaustive `match` on `Token` variants. These choices were not
   directed by the human.

## What the Human Did

1. **Authored the project constitution** — three hard rules that the
   agent must follow at all times:
   - CSSWG spec is ground truth (spec > WPT > Chromium when they conflict)
   - Safe Rust only (zero `unsafe`, zero C/C++ deps)
   - Spec-compliant, not test-compliant (never modify a test to pass it
     unless the spec proves the test is wrong, with chapter citation)

2. **Built the test-feedback loop** — a harness that runs
   `cargo test --lib`, captures per-test pass/fail, and feeds failing
   cases back to the agent with the expected token stream and the
   relevant CSS Syntax spec section.

3. **Reviewed every commit** — the human reads every diff before
   `git commit`.

## Test Results

- **Tokenizer**: 71/71 unit tests pass covering all 15 §4.3
  sub-algorithms, including edge cases for:
  - Whitespace run collapsing
  - Comment dispatch and unterminated comments
  - Numeric token disambiguation (`+`/`-`/`.` lookahead)
  - CDO/CDC token emission (`<!--`/`-->`)
  - Ident-like token dispatch (`url(` vs function vs ident vs at-keyword)
  - Hash type flag (id vs unrestricted)
  - String escape decoding (hex escapes, line continuation, bad-string)
  - URL token consumption (quoted/unquoted, escape, bad-url recovery)
  - Unicode-range token (wildcards, range form, max hex)
  - `unicode_ranges_allowed` flag default behavior
